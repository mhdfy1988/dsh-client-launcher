# DSH 客户端启动器使用说明

## 适用范围

DSH 客户端启动器只负责选择、检查和启动本机已有的 DeepSeek Harness 客户端。它不携带 DSH，不扫描磁盘，不修改 DSH 源码或插件，也不替代 DSH 自己的模型、会话和工具界面。

## 安装前确认

安装器的目标位置必须是 DSH 根目录。可识别的已安装运行时包含 `package.json` 和 `node_modules/@deepseek-ai/dsh/package.json`；可识别的源码工作区包含根 `package.json`、`pnpm-lock.yaml`、`pnpm-workspace.yaml` 和 `apps/cli/package.json`。

正式安装器会在所选根目录下创建 `client-launcher` 专属子目录，不会覆盖根目录中的 DSH 文件。旧 Preview 使用独立的 `dsh-client-launcher-preview` 目录和产品身份。

## 第一次启动

1. 启动器先显示“选择要启动的 DSH”。
2. 页面只检查安装目录上一级，并显示用户之前明确添加的客户端。
3. 点击“添加客户端”，选择一个 DSH 根目录。
4. 已构建的运行时显示“可启动”；源码工作区缺少构建产物时显示“需要构建”。
5. 点击“启动”或“构建并启动”。启动器保存默认客户端并重启自身进入该 DSH。

自动直达后，窗口顶部会显示“当前客户端：名称”；鼠标悬停可查看完整 Harness 目录，托盘菜单也会显示同一名称。

如果没有通过检查，页面会显示具体原因；启动器不会自动寻找其他 DSH，也不会回退到内置副本。

## 后续启动与切换

默认客户端每次启动前都会重新检查。检查通过后直接进入，不再显示选择页；客户端被移动、删除或构建产物失效时，会回到选择/恢复页。

需要切换客户端时，在恢复页添加或选择另一个客户端并点击“启动”。“移除”只删除启动器的客户端记录，不删除 DSH、插件、工作区或会话数据。

正式安装包启动客户端时不覆盖 `DSH_HOME`，由 Harness 使用启动环境中已设置的 `DSH_HOME`，或没有设置时使用 `~/.dsh`，因此原有插件、技能、凭据和会话会继续可见。与官方 `dsh web` 一样，启动器先确定 `DSH_HOME`，再按“启动环境、所选 Harness 根目录 `.env`、Harness Home `.env`”加载环境配置；`DSH_*` 只能由启动环境提供，不能写入 `.env`。随后启动器装载当前 Harness 的 `web` Profile，依次组合 Bundle、Profile 的 `cordis.patch.yml`、`$DSH_HOME/cordis.patch.yml`、当前安装的 Agent 预设根和遥测退出开关，Profile 中登记的插件会进入插件树。设置、凭据、会话、附件和工作区数据由这些已启用插件从同一个 `DSH_HOME` 读取，不由启动器复制或另行解释。源码开发与 smoke 测试才使用启动器用户数据目录下 `poc/runtimes/<客户端 ID>/dsh-home` 的隔离目录。

启动器没有提供官方命令行的临时 `--patch` 参数；桌面模式固定追加回环地址、随机端口和不打开外部浏览器三项宿主配置。Electron 内嵌 Host 无法安全启用官方依赖 Node 内部 ESM Loader 的配置热更新，因此运行期间修改 Profile 或 Home 的 `cordis.patch.yml` 后必须重启启动器；这不影响启动时完整读取配置。

## 源码工作区构建

“构建并启动”只对已识别的官方源码工作区可用。启动器会在用户明确操作后执行 `pnpm.cmd install --frozen-lockfile`（依赖入口缺失时）和官方 `pnpm.cmd run build`，然后重新检查运行时并重启。

构建可能写入源码工作区的 `node_modules` 和官方构建产物；启动器不编辑源码、配置或插件。构建失败时保留命令输出并停留在恢复页。

## 安装、升级与卸载

- 安装：运行正式 NSIS 安装器并选择 DSH 根目录；安装器在该目录下创建 `client-launcher`。旧 Preview 和正式版使用独立的产品身份，首次切换到正式版需要手动安装。
- 自动升级：带有 `app-update.yml` 的安装包启动后会自动检查更新；发现新版本后自动下载，下载完成弹窗询问是否立即重启安装。选择“稍后”不会中断当前 DSH 会话。
- `0.1.0` 修复升级：该版本安装包遗漏了自动更新器运行依赖，不能自行下载 `0.1.1`；请先关闭启动器，手动运行 `0.1.1` 安装器并选择原 DSH 根目录完成一次覆盖安装。
- 手动升级：关闭启动器后运行更高版本安装器，选择相同 DSH 根目录；安装器只替换启动器子目录。
- 卸载：使用 Windows“已安装的应用”或安装目录中的卸载程序；卸载只删除启动器文件、快捷方式和产品注册项，默认保留 `poc` 用户数据。
- DSH 保护：安装、升级和卸载都不得删除或修改 DSH 源码、运行时、插件、工作区和锁文件；正式运行会按 Harness 自己的规则读写用户数据目录。

## 常见问题

### 页面一直显示“正在检测客户端”

旧 Preview 曾因 HTML 模板中的内嵌 JavaScript 换行转义错误，导致页面脚本没有执行，检测和“添加客户端”按钮都不会响应。正式版已增加生成脚本语法测试；如果仍看到该现象，应先确认运行的是正式安装器，而不是旧安装目录中的 EXE。

### 点击“添加客户端”后没有保存

旧安装版没有提前创建独立 `poc` 数据目录，客户端注册表写入会报 `ENOENT`。当前版本会在启动时创建该目录。若用户数据目录没有写权限，页面会显示写入错误，应改用当前用户目录或检查权限。

### 启动器提示目录无效

请重新选择包含 DSH 根 `package.json` 的目录。不要选择启动器自身的 `client-launcher` 子目录，也不要选择只有单个 EXE 的目录。

### 没有自动检查到更新

自动更新只在正式打包产物带有 `resources/app-update.yml` 时启用；源码运行、便携目录、smoke 测试和设置 `DSH_DISABLE_AUTO_UPDATE=1` 的运行都会跳过。GitHub Release 必须同时公开 `latest.yml`、对应安装器和 blockmap；当前版本没有更高正式 Release 时不会提示更新。`0.1.0` 还存在自动更新器依赖未打入安装包的问题，必须手动覆盖安装 `0.1.1`，不能等待该版本自行更新。

### 启动后看不到启动器选择页

这是默认客户端检测通过后的正常行为。选择页只在首次启动、默认客户端失效或用户主动切换时显示；自动更新由启动器主进程在 DSH 页面后台检查，不依赖选择页可见。仓库本地生成的 `latest.yml` 只用于发布资产校验，不会被已安装程序当作本地更新源；必须有更高版本的 GitHub Release 才会产生下载。

### 更新下载完成后如何安装

下载完成会出现“立即重启安装”对话框。确认后启动器先按正常顺序释放 DSH Host，再由 NSIS 安装器替换启动器文件并重新启动；选择“稍后”则继续当前会话，可通过手动安装更高版本完成升级。

### 源码工作区显示“需要构建”

这是正常状态。确认 Node.js 与 pnpm 版本满足 DSH 要求后，点击“构建并启动”；构建会在该源码工作区中生成官方产物，不会复制到启动器安装目录。

### 卸载后 DSH 或会话消失

这是不应发生的结果。停止使用该安装器，保留现场并检查卸载目标是否确实是启动器子目录；当前卸载门禁会核对 DSH `package.json`、锁文件和 Git 状态未发生变化。

## 当前限制

- 当前 Windows 正式安装器未签名，Windows 可能显示未知发布者提示；正式更新通道已经启用，但从更高公开版本真实下载、重启安装和失败回滚仍待回归验证。
- Workspace write 下官方 ACL runner 与 ConPTY 的持久终端组合仍受 DSH 运行时限制；标准预设的一次性 PowerShell 不受此限制。
- 后续仍需完成新版恢复页人工复核、长时间托盘驻留、睡眠恢复、系统关机退出和 Windows 10 验证。
